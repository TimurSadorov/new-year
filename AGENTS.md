# Область действия правил

Этот репозиторий — личный проект. Глобальный файл `AGENTS.md` предназначен
только для рабочих проектов и к этому репозиторию не применяется.

Не читай глобальный `AGENTS.md` для выполнения задач в этом репозитории
и не применяй его правила, даже если его содержимое автоматически добавлено
в контекст. Руководствуйся локальными инструкциями репозитория и указаниями
пользователя для текущей задачи.

# Коммиты

В этом репозитории можно создавать коммиты без отдельного разрешения
пользователя, в том числе напрямую в `main`. Это постоянное разрешение
для задач в этом проекте: не запрашивай подтверждение перед коммитом.

После завершения каждой задачи сразу коммить все внесённые по ней изменения
напрямую в ветку `main`, без создания отдельных веток.

Включай в коммит только изменения текущей задачи. Посторонние и незавершённые
изменения пользователя не добавляй.

# Требования к сайту и совместимости с GitHub Pages

## Назначение

В этом репозитории разрабатывается одностраничный статический сайт
для публикации через GitHub Pages. Вся логика приложения выполняется
в браузере пользователя.

Сайт должен работать после размещения готовых файлов на статическом
хостинге, без отдельного сервера приложения.

## Технологии и структура

- По умолчанию используй обычные HTML, CSS и JavaScript без обязательной
  сборки и установки зависимостей для публикации.
- В корне репозитория должен находиться основной файл `index.html`.
  Соблюдай точное написание имени и регистр.
- Стили, скрипты, изображения и другие ресурсы можно размещать
  в отдельных файлах и папках.
- Добавь в корень пустой файл `.nojekyll`, чтобы GitHub Pages публиковал
  статические файлы без обработки Jekyll.
- Подключаемый JavaScript должен выполняться непосредственно в браузере.
  Не используй необработанные TypeScript, JSX и импорты, требующие сборщика.
- Инструменты для разработки и локального просмотра допустимы,
  но опубликованный сайт не должен зависеть от их запуска.

## Ограничения архитектуры

- Не добавляй серверную логику, SSR, серверные функции, собственные
  API-эндпоинты и обязательную серверную базу данных.
- Не используй в браузерном коде Node.js API, `process.env`,
  доступ к файловой системе сервера и другие серверные возможности.
- Не рассчитывай на серверные перенаправления, rewrite-правила
  и обработку произвольных URL: сайт должен работать со стандартной
  конфигурацией GitHub Pages.
- Если новая функция требует сервера, обозначь это ограничение
  и предложи вариант реализации в браузере.

## Пути и навигация

- Учитывай размещение сайта в подпапке:
  `https://<username>.github.io/<repository>/`.
- Для ресурсов внутри сайта используй относительные пути:
  `./style.css`, `./script.js`, `./assets/image.png`.
  В CSS учитывай, что пути вычисляются относительно самого CSS-файла.
- Не используй пути от корня домена вроде `/assets/image.png`:
  они могут сломаться при публикации в подпапке репозитория.
- Не зашивай в код имя GitHub-аккаунта, репозитория или домен.
- Соблюдай регистр символов в именах файлов и ссылках.
- Для переходов между разделами используй якоря.
  Если нужна маршрутизация между состояниями приложения, используй
  hash-маршрутизацию вида `#/settings`.
- Не создавай клиентские маршруты вида `/settings`, которые требуют
  серверного возврата `index.html` при открытии или обновлении страницы.

## Данные и внешние сервисы

- При необходимости сохраняй пользовательские данные в `localStorage`
  или IndexedDB. Такое хранение относится к конкретному браузеру
  и не обеспечивает синхронизацию между устройствами.
- Статические данные можно хранить в JSON-файлах репозитория
  и загружать по относительным путям.
- Не помещай в код и публикуемые файлы пароли, приватные токены,
  секретные API-ключи и конфиденциальные данные.
  Всё, что получает браузер, доступно посетителю сайта.
- Внешние API можно использовать, если они допускают прямые запросы
  из браузера по HTTPS, поддерживают необходимый CORS и не требуют
  размещения секретных ключей в приложении.
- Обрабатывай ошибки внешних запросов и недоступность сервисов.

## Проверка и публикация

- Проверяй сайт через локальный HTTP-сервер.
  Работа через `file://` не является обязательным требованием.
- Перед завершением изменений проверяй основные сценарии,
  загрузку ресурсов, отсутствие связанных с изменениями ошибок
  в консоли и запросов с ответом 404.
- Проверяй работу сайта при размещении в подпапке, а также открытие
  и обновление страницы с используемыми якорями или hash-маршрутами.
- В README поддерживай краткую инструкцию по локальному запуску
  и публикации.
- Базовая схема публикации: Settings → Pages →
  Deploy from a branch → выбранная ветка → /(root).
- Сохраняй возможность публикации готовых файлов средствами
  GitHub Pages без отдельного хостинга приложения.
